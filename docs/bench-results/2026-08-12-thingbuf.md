# thingbuf joins the bake-off: the closest prior art, measured

**Date:** 2026-08-12
**Hardware:** 4-core Linux VM, 15 GiB RAM, no swap; `vmstat` 84–88% idle,
0 runnable, 5.8 GiB free
**Method:** built to completion first; three full rounds of every cell,
interleaved by round; criterion mean per cell, reported as median-of-three with
range. All numbers from one session, so ratios within this document are valid
and absolute figures are not comparable to other sessions.

`thingbuf` 0.1.6 was surveyed on 2026-08-06 and called "the closest prior art":
a fixed-capacity `MaybeUninit`-slot ring with an MPSC channel layer, loom-tested,
the same shape as `src/mpsc.rs`. It is also load-bearing in `docs/design.md` —
§9 rejects Vyukov packed stamps citing thingbuf's issues #98 and #100. It had
never been measured. That gap is now closed.

## Three cells, because the by-value API is not thingbuf's API

- `thingbuf` — `try_send`/`try_recv`, by value. Like-for-like against the other
  polling cells.
- `thingbuf_ref` — `try_send_ref`/`try_recv_ref`, the crate's natural API.
- `thingbuf_blocking` — `send`/`recv`, in the blocking group.

> **Superseded in part, same day.** A `String` cell was added hours later
> (`2026-08-12-cpu-cost-and-heap-payload.md`) and it reverses the headline: on a
> heap-owning payload thingbuf's reference API is **1.82x this crate**, where on
> `u64` this crate is 3.89x ahead. Every number below is correct for the payload
> it was measured on. Do not quote the 4.85x without the 1.82x.

**The `u64` payload cannot show what slot recycling is for.** thingbuf's reason
for existing is that a `Ref<T>` lets the caller mutate a slot's existing value
in place, so a `String` or `Vec<u8>` payload keeps its heap buffer instead of
reallocating each pass. A `u64` owns nothing, so recycling has nothing to
recycle. Every number below is a measurement of thingbuf's *machinery* with none
of its *benefit*. No cell in this file uses a heap-owning payload, so nothing
here is a verdict on slot recycling.

## Two findings

### 1. thingbuf's by-value API costs 24% against its own reference API

18.66 against 14.99, ranges 17.58–18.96 and 14.54–15.35 — no overlap.

This is what the survey predicted from reading the source and is now measured:
`push`/`pop` are sugar over `push_ref`/`pop_ref` plus a `mem::replace`, so the
by-value path does everything the reference path does *and then some*. On a
`u64` the recycling step (`clone_from(&u64::default())`) buys nothing while
still costing. A caller who reaches for the familiar `try_send(v)` because it
looks like every other channel API pays 24% for the familiarity, on a payload
where the alternative would have gained nothing else.

### 2. Blocking beats polling for thingbuf, and loses badly for this crate

| Crate | polling | blocking | direction |
|---|---:|---:|---|
| `thingbuf` | 14.99 | 19.90 | blocking **+33%** |
| `ultima_rings` | 72.67 | 11.88 | polling **6.1x** |

Same box, same thread count, same payload, same capacity, opposite sign. So this
is not the machine — it is how each crate's blocking path is built.

This is the sharpest thing the new cells say, and it lands on a known weakness.
`Park` parks on the *first* empty observation with no spin before it, which is
exactly the mechanism `2026-08-11-backoff-isolation.md` identified as the likely
cause of the CAS backoff's `park_block` regression. thingbuf's blocking path is
**1.68x** this crate's `Park` — the second competitor after crossbeam to beat it,
and the first that is structurally the same kind of ring.

The obvious remedy, a short spin before the first park, was implemented and did
not survive its gate (`2026-08-12-layout-sensitivity.md`). This result says the
question is worth reopening with a better measurement rather than a better guess:
`park_block`'s ~11% minimum detectable effect is the reason that attempt could
not be resolved, and a 1.68x gap is far too large to be hiding under it.

## A bug found in thingbuf 0.1.6 while writing the cells

`TrySendError::is_closed()` returns `matches!(self, Self::Full(_))` — it tests
for `Full`, not `Closed`, so it returns `true` on a full channel and `false` on
a closed one. Both `is_full()` and `is_closed()` are the same predicate.

**Filed upstream 2026-08-14 as
[hawkw/thingbuf#101](https://github.com/hawkw/thingbuf/issues/101).** Writing the
reproduction turned up a second copy of the same mistake —
`SendTimeoutError::is_closed()` matches `Self::Timeout(_)` — and both are on
`main`, not only in the published 0.1.6.

A third bug surfaced while building the reproduction and is filed separately as
[hawkw/thingbuf#102](https://github.com/hawkw/thingbuf/issues/102): a
`send_timeout` that times out leaves a stale node in the sender wait queue, and
`debug_assert_eq!(_prev_state, WAITING)` in `List::dequeue` fires when the
channel is dropped. It is timing-sensitive and `debug_assert`-only, so release
builds run past it.

`src/mpsc/errors.rs:196-212` in 0.1.6:

```rust
pub fn is_full(&self) -> bool {
    matches!(self, Self::Full(_))
}

pub fn is_closed(&self) -> bool {
    matches!(self, Self::Full(_))   // <-- should be Self::Closed(_)
}
```

The cells here match on the variants directly and are unaffected, which is
probably why this went unnoticed for so long — the natural retry loop
(`Err(e) if e.is_closed() => return`) silently never terminates on a closed
channel.

## Harness change: the baseline moved into the group

`bakeoff_mpsc` had no cell for this crate. Its number came from
`mpsc/busy_spin_2_producers` in a different group — the same harness shape
byte-for-byte, so the prior comparisons were sound, but a filtered run of
`bakeoff_mpsc/` silently produced a competitor table with no baseline in it.
That happened once during this session. The cell now lives in the group.
